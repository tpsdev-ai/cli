- **The workflow npm guard reads `shell:` and restricts command-word shapes.** Step `shell:` overrides job defaults, which override workflow defaults; a non-`bash` shell refuses an unapproved run block, naming its source line. The guard refuses leading redirections and variable assignments containing `<` or `>` before a command word in unapproved run blocks. Command words containing `*`, `?`, `[` or `$'` are refused, except `[` and `[[` themselves. Prefix, option, wrapper and command-word matching read each word's static value, decoded with bash's quoting rules: inside single quotes every character is literal, a backslash included; inside double quotes a backslash escapes only `$`, a backquote, `\"`, `\\` and newline; outside quotes a backslash escapes the next character. A word containing a parameter, command, arithmetic or brace expansion, an unescaped backquote, an unquoted `~` or an unquoted glob has no static value. `env` accepts only leading `NAME=value` assignments followed by the command; every `env` option is refused, and `builtin` and `hash` are refused as unrecognised command words, in run blocks and followed shell files. The guard consumes the `sudo`, `exec` and `xargs` options from a finite grammar and refuses unmodelled options, including `sudo -s`/`-i`/`--shell`/`--login`. In an unapproved run block, a word with no static value in command position is refused, a plain variable command word excepted only when no prefix precedes it, and after a prefix every word up to and including the command word must have a static value; a followed shell file does not follow such a word. In unapproved run blocks, a backslash-newline continuation inside a word is refused, naming the physical line. In run blocks and followed shell files, a command word whose first decoded character is an unquoted `{` is refused, unless the `{` stands alone. In unapproved run blocks, the listed wrappers (`timeout`, `nice`, `stdbuf`, `setsid`, `chroot`, `ionice`, `chrt`, `taskset`, `flock`, `unbuffer`, `script` and `watch`) are refused outright; a `${{ ... }}` runner expression in command position is refused however it is quoted. Command-position `time`, `coproc`, `function`, `in` and `]]` are refused in unapproved run blocks; `!` is skipped before the assignment search. `case` in command position is refused in unapproved run blocks. In unapproved run blocks and followed shell files, an unclassified here-document header (including a continuation or quote) or body boundary refuses scanning, naming the physical line. Only unquoted `<<`/`<<-` operator tokens start here-documents; quoted `<<` text does not queue a delimiter. Modelled headers are single-line simple-command redirections with bare, single-quoted or double-quoted `[A-Za-z_][A-Za-z0-9_]*` delimiters, queued in source order; run-block headers must be top-level. Unquoted bodies join backslash-newline before delimiter comparison; quoted bodies compare literally; `<<-` strips leading tabs. Literal brackets in `${...}` defaults do not hide a following header; nested expansions stay opaque. These checks read top-level clauses only: commands inside `$(...)` or backtick substitutions, and text after a quote that spans physical lines, are not checked. This lint does not model compound commands; variable or substitution indirection and composite-action shells are not covered.
