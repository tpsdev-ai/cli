- **Mail placement intents carry a phase; MailClient recovery, the CLI lease sweep and promotion skip or preserve non-`placing` intents (Refs #617, slice a).** An intent without a `phase` is `placing`. An otherwise-valid older intent whose `file` is a plain basename is handled exactly as before, records with no intent are handled as before, and no writer emits another phase yet. On those paths, a record whose intent declares `in_progress`, or carries an unsupported value in `phase`, `version` or a liveness field, is never finished, replaced, presented or checked out. Such an intent is not quarantined solely for that value, and it keeps only its own file's delivery gate closed. An intent that declares `failed` leaves its per-file (filename) gate open, while its message ID stays refused by the consumed-ID (replay) gate; it is not presented on those paths. It stays until an operator removes it, and its payload follows ordinary `cur/` archive and GC retention. One exception to preserving a non-`placing` intent: once a `failed` payload has left `cur/`, a different message may reuse the name. Its placement moves the marker to `.placement-<hash>.failed-<messageId>.json`, which keeps the old consumed ID retained, if that tombstone name is unoccupied or is the marker's own inode (treated as an interrupted move). An occupied tombstone refuses the reuse by name and keeps both files, and the new message is not delivered. While the payload is still in `cur/`, the new message waits.

  A placement intent whose `file` is not a plain basename (empty, `.`, `..`, or containing `/`, `\` or NUL) is now refused on write and quarantined on read. That includes an older intent the previous parser accepted when its hashed name matched: the one exception to legacy parity.
