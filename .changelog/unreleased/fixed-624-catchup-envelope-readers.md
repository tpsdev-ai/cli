- **The task loop and `tps agent logs` read Flair's catch-up envelope rather than a list (Closes #624).** A `task.assigned` event now reaches the task handler, and `FlairClient.getEventsSince` returns the read's outcome, so a caller can tell an empty feed from an unreadable one.

  A read is unavailable, with a bounded reason, when the request is refused or fails, the signing key cannot be read, `since` is not a valid date, or a page fails validation (its envelope, its events' fields, positions and order, or a `nextAfter` that does not follow from them). `tps agent logs` then says the OrgEvents are unavailable and still shows mail; the task loop handles and persists nothing from that read.

  The task loop keeps its feed position in `~/.tps/cursors/<agent>-task-loop.json` as `{ position, updatedAt }`, written atomically, and sends it on every read. With no usable cursor file it sets the position one hour back, once, and persists it before the first read; an unreadable file is logged and treated as no cursor, and a legacy `{ since }` file resumes from its timestamp. `tps office status` shows the cursor's timestamp in either format.

  Delivery is at least once, not exactly once, under these conditions: the cursor file can be written and stays intact; the feed's pages pass validation; the feed only appends (a new event sorts after those already served), with positions within five minutes of the server's time; and an event does not expire before its handler succeeds. Then a task event's handler succeeds before the persisted position passes the event, and a failed event is retried, in the same process or after a restart, before any later one. A crash after a handler returns and before the position is written replays the event, so handlers must be idempotent.
